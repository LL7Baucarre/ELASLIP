STIX 2.1 Overview

STIX (Structured Threat Information Expression) 2.1 is a standardized language for communicating cyber threat intelligence. All indicators and objects in ELASLIP are stored as valid STIX 2.1 objects.

Key Concepts
  • Indicator: A STIX object that contains a pattern for detecting potential IOCs (Indicators of Compromise)
  • Pattern: A query-like expression that defines what to look for (e.g., file hashes, IP addresses)
  • Objects: Malware, Threat Actors, Campaigns, Tools, Attack Patterns, etc.
  • Relationships: Links between objects showing how they relate to each other
STIX Object Timestamps

Every STIX object has:

  • created - When the object was first created in ELASLIP
  • modified - When the object was last updated
  • valid_from - When the intelligence becomes valid (IOC indicator field)
  • valid_until - When the intelligence expires (IOC indicator field)
Custom ELASLIP Metadata

ELASLIP extends STIX with the x_metadata field for platform-specific data:

  • tlp - Traffic Light Protocol level (white, green, amber, red)
  • confidence - Confidence level (low, medium, high)
  • threat_level - Threat severity (low, medium, high, critical)
  • source - Where the intelligence came from
  • campaigns - Associated campaigns
  • labels - Custom tags and categories
  • versions - Previous versions of the object
Indicators & IOCs

Indicators are STIX objects that encapsulate patterns for detecting malicious activity. Each indicator contains:

IOC Types Supported
Type Description Example
ipv4 IPv4 Address 192.0.2.1
ipv6 IPv6 Address 2001:db8::1
domain Domain Name example.com
url Full URL https://example.com/malware
md5 MD5 Hash 5d41402abc4b2a76b9719d911017c592
sha1 SHA1 Hash aaf4c61ddcc5e8a2dabede0f3b482cd9aea9434d
sha256 SHA256 Hash e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
email Email Address attacker@example.com
asn Autonomous System Number AS15169
file-path File Path C:\Windows\System32\malware.exe
registry-key Registry Key HKEY_LOCAL_MACHINE\Software\Malware
process-name Process Name svchost.exe
mutex Windows Mutex Global\MalwareMutex
certificate-serial SSL Certificate Serial 00:d0:b2:ee:b5:f1:89:c0
IOC Fields
  • Type: Category of the indicator (from the list above)
  • Value: The actual indicator value
  • Pattern: Auto-generated STIX pattern for detection
  • Labels: Free-text tags (malware, c2, phishing, etc.)
  • Source: Origin of the intelligence
  • Threat Level: low, medium, high, critical
  • Confidence: low, medium, high
  • TLP: white, green, amber, red
  • Campaigns: Associated threat campaigns
  • Valid From/Until: Time window for validity
Deduplication

IOCs are automatically deduplicated based on (type, value) tuples. Adding the same IOC twice will create a new source link rather than duplicate the indicator.

Relationships

Link IOCs together to show relationships such as:

  • IOC A communicates with IOC B
  • File hash belongs to malware family X
  • Domain is hosted on IP address
Cases

Cases are investigation containers that group related IOCs, incidents, and activities around a specific security event or campaign.

Case Lifecycle
  • Open: Initial state when case is created
  • In-Progress: Active investigation underway
  • On-Hold: Investigation paused, waiting for additional information
  • Closed: Investigation completed
Case Structure

A typical case contains:

  • Title & Description: What is this case about?
  • Priority: low, medium, high, critical
  • Status: Current investigation state
  • Owner: Primary investigator responsible
  • Linked IOCs: Indicators associated with this case
  • Incidents: Security events that occurred as part of this case
  • Timeline: Chronological record of events and actions
  • Comments: Threaded discussion and notes
  • Checklists: Tasks to complete for the investigation
Case Workflow Tips
  • Create a case when you identify a security event requiring investigation
  • Link all related IOCs to the case for unified tracking
  • Create incidents within the case to document specific malicious activities
  • Use the timeline to document discovery and analysis steps
  • Add comments for team collaboration and technical notes
  • Generate AI-powered reports to summarize findings
Case Statistics

Cases track:

  • Total IOCs linked
  • Number of incidents
  • Timeline events
  • Days investigation has been open
Incidents

Incidents represent specific security events within a case. They capture the details of what happened, when, and on which systems.

Incident Lifecycle (NIST IR Phases)
  • Investigating: Initial detection and investigation phase
  • Containment: Stopping the attack and preventing spread
  • Eradication: Removing the threat completely
  • Recovery: Restoring systems to normal operations
  • Closed: Incident fully resolved
Incident Core Fields
  • Title: Summary of the incident
  • Description: Detailed incident description
  • Severity: critical, high, medium, low
  • Status: Current investigation phase
  • Detection Time: When the incident was first detected
  • Occurrence Time: When the malicious activity actually began
  • Affected Systems: Hosts, networks, or services impacted
MITRE ATT&CK Integration

Incidents can be tagged with MITRE ATT&CK framework identifiers:

  • Tactics: High-level adversary goals (Reconnaissance, Exploitation, C2, Exfiltration, etc.)
  • Techniques: Specific methods used to achieve tactics (T1566 - Phishing, T1098 - Valid Accounts, etc.)

This helps categorize attacks and compare them to known threat actor behaviors.

Incident Report Sections

Incidents support detailed multi-section reports:

  • Executive Summary: High-level overview for management
  • Technical Analysis: Deep-dive technical investigation
  • IOC Summary: Indicators discovered during investigation
  • Impact Assessment: Business and technical impact
  • Recommendations: Remediation and prevention steps
  • Lessons Learned: Future improvements and process updates
Incident Workflow
  1. Create incident when malicious activity is detected
  2. Record detection time and when activity likely began
  3. Link relevant IOCs to document malicious infrastructure/artifacts
  4. Update status as investigation progresses through NIST phases
  5. Document technical details in report sections
  6. Generate AI-powered analysis for faster documentation
  7. Close incident when fully resolved

Checklists

Checklists are task lists used during investigations to ensure nothing is missed. They can be created from templates or customized for specific needs.

Types of Checklists
  • Response Checklists: Incident response playbooks and procedures
  • Investigation Checklists: Steps to investigate specific attack types
  • Containment Checklists: Actions to isolate and contain threats
  • Recovery Checklists: System restoration procedures
  • Custom Checklists: Organization-specific procedures
Checklist Structure

Each checklist contains:

  • Title: Name of the checklist
  • Description: Purpose and use case
  • Items: Individual tasks with descriptions
  • Assigned To: Team member responsible
  • Status: Not Started, In Progress, Completed
Checklist Item Fields
  • Title: Task description
  • Description: Detailed instructions or context
  • Completed: Checkbox to mark task as done
  • Assigned To: Responsible team member
  • Due Date (optional): Target completion date
Using Templates

Checklist templates provide standardized procedures:

  • Create reusable templates for common incident types
  • Clone a template to create a new checklist quickly
  • Share templates across the organization
  • Update templates based on lessons learned
Checklist Best Practices
  • Create checklists at the start of investigations
  • Assign items to specific team members for accountability
  • Update progress regularly during active response
  • Mark items complete when verified, not assumed
  • Use templates to standardize critical procedures
  • Review completed checklists in post-incident reports
Checklist Reports

Generate AI-powered reports from completed checklists to:

  • Summarize response actions taken
  • Document what was completed vs. pending
  • Create compliance evidence
  • Support incident documentation
STIX Pattern Format

STIX patterns are filter expressions that define detection logic. ELASLIP automatically generates patterns from IOC type and value, but here's how they work:

Pattern Examples

IPv4 Address Detection:

[ipv4-addr:value = '192.0.2.1']

File Hash Detection:

[file:hashes.MD5 = 'd41d8cd98f00b204e9800998ecf8427e']

Domain Detection:

[domain-name:value = 'example.com']

URL Detection:

[url:value = 'http://example.com/malware']

File Path Detection:

[file:name = 'malware.exe']

Registry Key Detection:

[windows-registry-key:key = 'HKEY_LOCAL_MACHINE\\Software\\Malware']
Pattern Operators
  • = - Equals
  • != - Not equals
  • LIKE - Pattern matching
  • IN - In list
  • AND - Logical and
  • OR - Logical or
Composite Patterns

Multiple conditions:

[file:hashes.MD5 = '5d41402abc4b2a76b9719d911017c592' AND file:name = 'malware.exe']

Alternative values:

[ipv4-addr:value = '192.0.2.1' OR ipv4-addr:value = '192.0.2.2']

Security & Compliance
Traffic Light Protocol (TLP)

TLP levels control information sharing:

  • TLP:White - Unlimited distribution
  • TLP:Green - May share within community
  • TLP:Amber - Limited to participants on need-to-know
  • TLP:Red - Not for distribution, internal use only
Audit & Compliance

Every action in ELASLIP is logged:

  • Who made changes (user attribution)
  • What changed (before/after values)
  • When changes occurred (timestamps)
  • From where (IP address)

Access the Activity log to review the complete audit trail.

Role-Based Access Control (RBAC)

Fine-grained permissions control who can:

  • Create, view, edit, or delete IOCs
  • Manage cases and incidents
  • Generate reports
  • Configure integrations
  • Manage users and roles

See Settings → Users for permission management.

API & Automation

ELASLIP provides a complete REST API for programmatic access. See the Interactive Swagger UI for complete API documentation with live testing.

API Authentication
  • Session-based: For web browser access
  • Token-based: For API client access (prefixed with ioc_)
  • OAuth: Integration with Google, GitHub, OIDC providers
Generate an API Key
  1. Go to Settings → API Keys
  2. Click "Create API Key"
  3. Provide a name and select scopes (permissions)
  4. Copy the key (shown only once)
  5. Use in requests: Authorization: Bearer ioc_your_key
Common API Operations

Create an IOC:

POST /api/ioc
Content-Type: application/json

{
  "type": "ipv4",
  "value": "192.0.2.1",

GET /api/search?query=192.0.2&threat_level=high&page=1&per_page=20

Common Workflows
Workflow 1: Threat Intelligence from External Feed
  1. Import IOCs from threat intelligence feed (JSON, CSV, STIX)
  2. Review and validate imported indicators
  3. Create case for related threat campaign
  4. Link IOCs to case
  5. Add labels, threat levels, and TLP marking
  6. Share case with team via webhooks or export
Workflow 2: Incident Investigation & Response
  1. Create case when security event is detected
  2. Create incident(s) documenting malicious activities
  3. Link IOCs (attacker IPs, domains, file hashes)
  4. Create checklist from response template
  5. Assign tasks and track completion
  6. Document timeline of events and actions
  7. Generate incident report with AI assistance
  8. Close incident and document lessons learned

  1. Collect indicators from multiple sources
  2. Import into ELASLIP via API or bulk import
  3. System automatically deduplicates by (type, value)
  4. Enrichment APIs run automatically to add context
  5. Review and validate enriched indicators
  6. Export deduplicated list for defensive deployment
Workflow 4: Compliance & Audit
  1. Configure role-based access for sensitive data
  2. Set TLP markings on sensitive indicators
  3. Review audit logs regularly (Settings → Activity)
  4. Generate compliance reports
  5. Export case/incident reports for documentation
Troubleshooting & Tips
Issue: IOC not appearing after import

Solution: Check that you have the ioc.view permission. IOCs may be filtered by threat level or search term. Clear search filters and reload.

Issue: Can't link IOC to case

Solution: Ensure you have case.edit permission. Verify the IOC and case both exist and aren't in deleted state.

Issue: Enrichment API not running

Solution: Check that API configuration is enabled in Settings. Verify API endpoint is reachable and returns valid JSON. Check application logs for errors.

Tip: Using Labels Effectively

Use consistent label naming for better filtering and reporting. Common labels include:

  • Attack type: malware, phishing, ransomware, apt, data-exfil
  • Source: threat-feed, customer-report, incident-response
  • Status: unconfirmed, confirmed, whitelisted
Tip: Effective Case Names

Use descriptive names with date/timeline:

  • "Ransomware-Deployment-Finance-Dept-2024-Q1"
  • "APT28-Campaign-Detection-Jan2026"
  • "Third-Party-Breach-Investigation"
Tip: Leveraging LLM Reports

  • Response procedure verification
Tip: Organizing with Campaigns

Tag related indicators with campaign names to group threat intelligence:

  • Tie together IOCs from the same threat actor
